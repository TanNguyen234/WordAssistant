# Software course report / capstone starter

Use this starter for a course essay, software project report, or đồ án chuyên ngành. The required depth is the same regardless of the document label: follow the assignment, rubric, selected institutional profile, and verified project evidence. Use StrongWine as a full-report example and depth checklist. Its headings, figures, tables, and page count are specific to that report; they are never quotas for another project.

Follow `docs/strongwine-course-essay-workflow.md` in order. Read `docs/strongwine-course-essay-lessons.md` for verified failure causes and prevention.

## Start each project

1. Create a new workspace with `python scripts/init_course_essay_project.py PATH --title 'Verified title'`. The destination must not already exist.
2. Fill `task-brief.md` before drafting. Keep the active request, controlling sources, acceptance checks, constraints, canonical input/output path and hash, latest matching QA, blockers, and next action in one short place. Update it before editing whenever the user adds or changes a requirement. On resume, load the brief and only the current artifact/QA needed for the next decision.
3. Record `document_type`, `course_name`, title, supervisor and each authority separately in `project.json` and `cover-metadata.csv`. A reference sample is never an authority for identity, approvals, signatures, project claims or results.
4. Record the assignment or a faithful summary, selected profile, and read-only source root and revision. Inspect every selected-profile `source_assets` file and user-supplied copy before declaring an official rubric missing. The starter defaults to including requested official rubric/criteria in the Word report. Map every exact criterion in `requirements-matrix.csv`; distinguish explicit assessment criteria from scoring levels/weights. If neither is present, do not infer one: keep the check `NOT_RUN` and submission readiness incomplete.
5. Before writing, draft the complete outline from the assignment, rubric, profile and verified project scope. Compare its depth with StrongWine's report groups: front matter/forms where applicable; abstract and lists; background/related work; current system and requirements; business/function models; OO analysis/design; architecture/data/components; implementation/UI; testing/evaluation/limitations; conclusion/future work; references and appendices. For every group, record whether it is required, adapted, or not applicable with a reviewer-approved reason. Include all actual final headings, including generated lists and references; do not shorten because the work is called a course essay.
6. Put one row per planned Word heading in `structure-parity.csv`. Its row count is project-specific. Record whether each heading must appear in the TOC. The checker compares the outline and the visible TOC entries separately by text, level and order. The reviewer must confirm the outline covers the entire assignment/rubric/profile and uses StrongWine to check depth; the checker cannot discover a requirement that was never entered in the matrix.
7. Put one row per actual planned figure, diagram, wireframe, screenshot, table, or decorative image in `asset-parity.csv`, in the order they appear in the DOCX. Its row count is project-specific. Record source, exact location, evidence, target section, expected media count, and `caption_required=true|false`; captioned rows need the exact final caption, while uncaptioned rows need a blank caption and a precise location (for example, each cover logo). A native Word table usually has zero embedded images; an image artifact has at least one. The checker verifies captions, total media, and image counts between captions, while separately accounting for declared uncaptioned media in document order. A reviewer still confirms that each image depicts the intended source/route. If no visuals are required, record `visual_inventory_review` in `project.json` with `decision: NONE_REQUIRED`, a reason, reviewer and date, and ensure the DOCX has no unplanned embedded images.
8. Build `acceptance-crosswalk.csv` before editing. Use one row per discrete user instruction, applicable guide/rubric requirement, and report quality check. Every project must cover `user_requirements`, `guide_requirements`, `assignment_rubric_requirements`, `heading_toc`, `abstract`, `screen_hierarchy`, `runtime_screenshots`, `diagrams`, `visual_content`, and `argument_citations`. Each completed row names the authority and location, criterion, report location, verification method, review evidence path and SHA-256, reviewer/date and exact final DOCX SHA-256. Keep rows `NOT_RUN` until checked; a stale hash or missing category/evidence blocks content readiness.
9. Read only source files needed for the report. Record routes/templates in `screen-inventory.json`, visuals in `figure-plan.csv`, and UML/ERD questions and source symbols in `diagram-plan.csv`. Select diagrams from the project and rubric: for UML, record exact source classes/methods/schema and what question the diagram answers; for database diagrams, inspect actual entities/migrations; for web screens, use actual GET routes/templates and mark POST/API calls as actions. Keep project source read-only.
10. For UML, write editable `.puml` from verified source symbols, then render with `python -m wordassistant.cli plantuml render INPUT.puml --output OUTPUT.png --format png --json`. Keep source and rendered image. A successful render proves syntax/rendering only; the reviewer compares every node and relation with source.
11. For screen hierarchy, enumerate actual GET views in `screen-inventory.json`; represent POST/API actions as actions/interfaces, never as pages. Use `python scripts/build_course_essay_assets.py render --inventory PATH --wireframe-dir PATH --diagram-dir PATH --report PATH` after manually verifying routes/templates. Use its `build` mode only for its supported Java Spring MVC adapter. The render-only report explicitly does not verify source routes.
12. Draw wireframes with the controls and labels found in the actual templates, simple black lines on white, empty data, and no invented controls. Keep wireframes distinct from runtime captures. Capture each runtime route by visible UI navigation from the website entry point; never open a local interface file or paste the target route into the address bar. For every attempted page, save a screenshot and hash of the actual visible state. Record HTTP/document status, console errors/warnings, timezone-aware timestamp, click path, and a hash-bound `page_state_review`; preserve error-page screenshots and mark failures so readiness cannot pass. Leave unsafe or unattempted routes `NOT_RUN` with a reason.
13. Compose/edit a new DOCX copy with WordAssistant. Use real Word styles, fields, captions, TOC/list fields and page numbers. When `include_official_rubric_in_docx` is true, preserve a standalone rubric as a complete appendix or copy all explicit criteria from a larger official guide into its corresponding review page. Record source/output hashes, authority, exact section markers or appendix heading, review details and whether scoring levels/weights are absent. The readiness checker compares full appendix text or marker-bounded source sections. Missing, scanned, image-bearing selected criteria, partial, or unreadable sources remain incomplete; never invent a replacement. Cite checked academic sources via `report-evidence.json`; track project facts separately in `claim-evidence.csv` and `evidence.json`.
14. Update fields in Word, save, render the saved DOCX and inspect every page. After any DOCX change, rerender and review the final file again. Correct clipping, unexpected color, spacing, crop or missing caption before final QA.
15. Save the raw verify, profile-validation and integrity-audit JSON. Disposition every integrity warning in `integrity-warning-dispositions.csv`. Keep all reports bound to the same output path and hash.
16. Run `python scripts/check_course_essay_readiness.py PATH_TO_WORKSPACE`. It is read-only. Report Word delivery, content/sources, and submission readiness separately. A Word delivery `PASS` does not imply rubric compliance or submission readiness.

## Project files

- `task-brief.md`: compact active handoff; update when a user requirement or current output changes. It points to authority and QA but does not replace source records.
- `project.json`: identity/authority, assignment/profile/source, output path, QA paths and manual acceptance records.
- `rubric_inclusion`: when rubric/criteria inclusion is requested, source authority/hash, exact appendix heading or source/output section markers, review method/status, reviewer/date, and final DOCX hash.
- `cover-metadata.csv`: authority and review status for visible identity fields.
- `requirements-matrix.csv`: variable set of rubric requirements mapped to report sections/evidence.
- `structure-parity.csv`: blank project-specific heading and TOC plan; no sample headings are preseeded.
- `asset-parity.csv`: blank project-specific visual plan, including expected embedded-image counts and whether captions are required; no sample images/tables are preseeded.
- `acceptance-crosswalk.csv`: per-criterion coverage and current-hash review record for user, guide, rubric and report-quality requirements.
- `screen-inventory.json`, `figure-plan.csv`, `diagram-plan.csv`: route/template, capture and editable diagram provenance.
- `claim-evidence.csv` and `evidence.json`: reviewed claims about the project and their source evidence.
- `report-evidence.json`: reviewed academic source registry used by WordAssistant citations.
- `integrity-warning-dispositions.csv`: one human disposition per current audit warning.
- `output/` and `qa/`: final DOCX and its matching delivery/content evidence.

Set a manual acceptance check to `true` only after a person completes and records that review. Do not infer missing facts. Keep the report `INCOMPLETE` where a required source, rubric, or review is missing.
